# SecRandom 集成协议 v1

v1 协议仅限本地使用。各实现使用当前用户的 IPC 端点与包含官方 proof 的发现清单。ECDSA P-256 签名涵盖 SDK 包 ID、程序集版本以及 SDK 客户端程序集的 SHA-256 哈希值；清单中的应用 ID 和显示名由接入应用提供，不属于签名范围。宿主检查所通告的进程是否已加载具有该哈希值的程序集，通信时核对 IPC 对端进程。在这些检查通过且用户批准该通知通道之前，清单均不可信。批准结果由 SecRandom 宿主持久化保存。官方 proof 证明客户端程序集来源，不证明使用它的第三方应用是官方应用。

SDK 抽取 API 仅公开 `random` 和 `fair`；它有意不包含编排模式。通知接收器接受 `notification.result`。宿主集成还保留了 `linkage.acquire` 和 `linkage.release`，用于浮动窗口抑制租约。除当前操作系统账户外，不暴露任何端点。

## 宿主中的通知渠道管理

SecRandom 在 `settings.linkage` 页面管理已经通过官方验证的渠道。发现 SDK 后，宿主先验证官方 proof、SDK 程序集哈希和进程存活状态，再弹出批准对话框；用户批准后才写入 `data/config/integration-channels.json`，通信时另行核对 IPC 对端 PID。渠道管理扩展见 [本体 PR #358](https://github.com/SECTL/SecRandom/pull/358)。

每个已批准渠道可以单独设置：

- 自定义显示名。该名称只用于宿主设置页，不改变 `app_id`、签名校验或 IPC 地址
- 结果发送开关。关闭后仍保留批准记录，但宿主不会发送 `notification.result`
- 浮窗联动开关。关闭后该渠道不能申请 `linkage.acquire`；已有租约会立即释放，浮窗按原状态恢复
- 删除。删除批准记录并释放该渠道的所有租约；同一进程的当前实例不会在后台循环中反复弹窗，新实例重新出现时仍会要求批准

“立即扫描”只重新读取当前用户的 SDK 清单目录。宿主没有“手工添加 IPC 地址”入口，这是有意的：自定义管理的是已验证渠道的本地策略，不能绕过官方签名验证创建任意通知端点。SDK 重启后，宿主会更新进程号、实例号、端点和最后在线时间，同时保留用户的显示名和两个开关。
